# M3.2 — provider-neutral tool foundation (development branch)

This is a narrow incremental slice of the future M3 agent runtime, not a
completed M3 milestone. It is based on the profile/memory work under PR #12
and the external interoperability design merged as PR #11.

## Implemented on this branch

- `ToolDescriptor` and `ToolRegistry` are CHOMIII-owned Java types with no
  Gemini/OpenAI SDK imports. Unknown or duplicate tool names cannot be
  dynamically registered. Only explicitly constructed per-turn tools are offered.
- `ToolTurn` adapts the neutral descriptors to the existing `ChatProvider.Tools`
  port. That port still provides bounded per-turn invocation and structured
  errors; `GeminiProvider` alone adapts the port to native Gemini calls.
- `memory.search` uses the neutral descriptor, while retaining existing
  owner-specific creation, validation, provenance and per-turn limits.
- New read-only `time.now` returns a real clock instant, local date/time,
  day of week and UTC offset for an explicitly provided IANA time zone;
  it defaults to UTC and never infers the person's location.
- `time.now` is feature-flagged OFF by default:
  `chomiii.tools.time.enabled=true`. It remains available when personal
  memory recall is disabled, because it needs no personal memory.
- Write-capability descriptors are not advertised or executable through this
  registry, even if a write implementation is accidentally passed in.
- Unit tests include deterministic clock output, invalid inputs,
  duplicate registration, blocked write tools, and a fake provider path
  through `ChatStreamService`.

## Not implemented / merge gates

- No persistent tool-call audit table, policy permits, user-facing approval,
  durable execution receipt, tool retry or multi-provider inference adapter.
  An existing provider-neutral *schema* does not by itself prove another model
  provider can complete a function-call continuation.
- No external web, Gmail, Calendar or MCP connection is available here.
- The tool budget is currently two calls and four seconds of cumulative
  tool execution per turn. Any expansion requires latency and safety review.
- Run backend and database integration suites locally, frontend checks,
  and a small live Gemini `memory.search` / `time.now` continuation study
  before merging. Repository CI has been unavailable due to a billing issue;
  no passing CI or local execution is claimed for these new commits.

## Proposed remainder of M3

- **M3.2:** finish the Java-owned policy gate: resolved owner, exact tool
  arguments, allowlisted tool ID, read vs write risk, explicit approval binding,
  cancellation, per-turn budget, and audit envelope. The current read-only
  registry is merely the first slice.
- **M3.3:** implement the first genuinely state-changing everyday action,
  such as a reminder or to-do, with a preview/approve/reject flow, real
  persistence, idempotency and exact-action receipts. Reuse backend patterns
  from old PR #5, not its standalone Tasks-panel UX. Use a new Flyway
  migration number; #12 already occupies V4/V5.
- **M3.4:** adaptive plan → permitted tool → observation → plan revision;
  show meaningful user-facing progress and ask only necessary questions.
  Keep the bounded model/tool loop and correct failure/cancellation handling.
- **M3.5 (new proposal, not yet a defined milestone):** harden the in-chat
  experience and acceptance tests: reliability, approval UX, negative-policy
  scenarios, useful progress summaries, provider-mock e2e evaluation and
  semantic task success. Do not treat this as durable autonomy.

## M4 and beyond

M4 is **external integrations**, not a second planner: implement trusted
connectors for web search, Calendar, Gmail and MCP with owner-bound OAuth,
scoped permissions, secret-handling, untrusted-output controls and connector
failure tests. Start with one small read-only API; then authorized writes.
M4.5 is a separately proposed multi-model-provider inference effort.
M5 owns scheduled/long-running tasks, restart recovery and retry safety.
