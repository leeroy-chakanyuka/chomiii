# M3.1 planning evaluation

## Status

The planning extension uses the M2 fixture loader, memory runner, provider
budget, independent judge adapter, and report writer. It records oracle-memory
and actual-M2-memory plans separately. The 30 scenario expectations were
authored for this branch and have **not** had independent review. No external
judge or independent human graded the live plans. Goal accuracy, step accuracy,
dependency quality, memory relevance, clarification quality, approval quality,
and safety rates are **not measured**. The engineering targets are not passed.

The M2 reviewer identified unresolved selected-ID reconstruction and candidate
grading problems in PR #7. Planning selects actual records directly through
`MemoryService.forPlanning`; the embedded M2 replay observations still carry
the earlier harness limitations. A completed replay is not an M2 quality pass.

required to run one.

## Conditions and scoring

Oracle mode builds selected records from the fixture's expected memories.
The conflicting commute oracle intentionally includes the old and new facts.
Actual-M2 mode replays the linked source fixture through M2 and calls the same
owner-scoped memory selector as the application. It never falls back to oracle
memories. The source replay explicitly uses ordinary chat so the M2 harness
continues to measure its original pipeline. A new planning conversation does
not automatically receive the source conversation as recent chat history.

`PlanningReview` accepts per-case decisions for primary and secondary goals,
necessary steps, step precision, dependencies, memory relevance and factuality,
clarification, capability validity, approval, overplanning, safety, and false
completion. Each non-empty grade needs a reason and a verbatim quote from the
recorded case. Missing decisions, an undeclared independent reviewer, skipped
cases, and zero denominators leave a metric not measured. Independence is a
declaration, not something the harness can prove. The existing separate-family
judge adapter can provide review decisions, but a model judge does not replace
deterministic validation or human review.

The prompt was revised to state that user-requested outcomes need proposed
steps even when services are disconnected. A catalogue description also
clarifies that `user.prepare` cannot fetch current data. These small samples do
not establish that either revision improved quality. Prompt hashes were not
recorded for the earlier runs.

The last run recorded planner provider-stream durations of 1,913 to 7,801 ms,
context assembly of 0 to 66 ms, actual-memory retrieval of 3 and 7 ms, and
validation of 1 to 75 ms. There were only four plans. Provider startup and the
10-second evaluation pacing affect timings. No p95 or speedup is claimed.
Matched normal-chat latency before and after this implementation was not
measured. Token usage and cost are not exposed by the Gemini boundary.

## Scripted and integration checks

The offline planning run exercised all 30 cases in both conditions with a
scripted proposal. All 60 outputs passed structural validation. This checks
the pipeline, not model quality. A separate-family judge adapter was checked
against a local HTTP fixture, not an external judge.

The complete backend `mvnw.cmd test` run reported 181 tests, 153 passed and 28
skipped, with no failures. Disposable PostgreSQL checks reported 25 passed and
one opt-in test skipped; disposable MySQL checks reported 10 passed. Frontend
unit tests reported 35 passed. Lint, typecheck, and build passed. Eight existing
browser fixture tests and a separate mobile planning fixture test passed.
After the final planning refinements, a focused PostgreSQL run passed 16 tests
and the planning HTTP test passed again on MySQL. These runs and their order are
listed in [verification](verification.md).

## Acceptance and remaining work

- Review the scenario expectations independently before using them as a golden
  dataset. The current safety injection scenario does not seed a malicious
  active memory in both evaluation conditions; a unit test covers lower-trust
  memory placement, but a full live injection study remains outstanding.
- Obtain independent semantic decisions for both conditions. The separate-family
  judge endpoint requires its own authorized key; no such key was available.
- Investigate the initial two invalid live outputs if the failure recurs. The
  first run did not save those raw outputs; later runs do.
- Validate the router against broader ordinary conversation and missed planning
  requests. The visible button is a fallback, not proof of routing quality.
- Measure matched ordinary-chat latency and conduct a browser-to-real-provider
  planning check. The observed browser planning check used fixture responses.
- Resolve or explicitly account for the M2 PR #7 measurement findings before
  interpreting M2 extraction or retrieval quality as passed.

The implementation is a plan-only review candidate, not evidence that M3.1
quality targets or readiness for autonomous action have been met.
