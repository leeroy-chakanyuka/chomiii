# M3.1 topic memory consolidation (#9 → #12)

PR #9 originally added an on-demand topic grouping and context vocabulary after M3.1
planning was observed to retrieve too few memories. PR #12 supersedes that original
inference-time grouping with a persisted, provenance-linked derived profile
and one canonical lexical/topic retriever. Do not reintroduce the obsolete
`MemorySelector` or `MemoryTopics` classes in parallel.

## Preserved from #9

- The per-message "Use saved memories" composer switch is moved into the
  Memories panel; the chat request still carries an explicit recall opt-out.
- The model catalogue includes the optional Gemini 3.5 Flash choice, subject
  to actual project/model availability and quotas.
- Planning instructions distinguish information already in context from details
  obtainable with a future read-only tool; existing constraints and preferences
  should not be solicited repeatedly.
- The canonical `MemoryRetrieval` retains a conservative adjacent-context
  bridge: a dinner request can use saved location and food information,
  and interview preparation can use schedule context.
- Regression checks cover topic association, unrelated questions, profile
  budget behavior, and suggested-memory exclusion.

## Behavior and boundaries

Initial context remains intentionally broad: stable work, location, education,
and project paragraphs can be included proactively. That preserves useful
context without requiring the model to discover every detail through a tool.
Context is bounded by the usual chat window and separate memory budgets.
`memory.search` is a second, selective retrieval path for additional context,
not a replacement for the initial profile.

The derived profile is not a separate source of truth. Only active canonical
memories contribute; saved corrections and deletions invalidate derived data.

## Conflict handling (initial conservative gate)

Automatic memory learning now detects a narrow set of explicit, same-slot
changes (residence and commute mode). A conflicting new candidate stays
suggested and cannot be approved until the existing fact is edited or removed.
No existing memory is silently deleted, and no model inference is allowed to
decide that two arbitrary statements contradict each other. Other kinds of
contradiction are not yet solved; add reviewed scenarios and a richer
user-visible conflict workflow before treating this as comprehensive.

## Evaluation still required

- Independent multi-turn tests for contradictory facts, revisions and user review.
- Provider-selected `memory.search` decisions and final answer quality, not
  just scripted lookup scores.
- A/B answer-quality comparison of broad initial profile + optional tool lookup
  against lexical-only memory and no memory.
- End-to-end frontend, MySQL, PostgreSQL and provider runs. Local tests reported
  in #12 predate this consolidation and do not verify its changes.
