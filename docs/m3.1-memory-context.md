# M3.1 follow-up: internal topic memory and retrieval

## Why

Review of M3.1 PR #8 uncovered that memory was present in the planner but the
selector depended on exact word overlap and returned at most three facts.
In a multi-intent user scenario (reschedule meetings, arrange dinner, protect
an interview), the visible plan cited an interview fact repeated from the
conversation and failed to demonstrate useful recall of older preferences.
Because this was a freshly started assistant, the observation is **not**
evidence that saved older context existed or that memory learning was broken.

## Model of memory

Claude's public help documentation describes a topical memory system (it moved
away from its legacy daily synthesis in July 2026). This implementation
adapts the *idea*, not Claude's proprietary architecture:

1. The M2 `personal_memories` rows remain canonical and owner-scoped.
2. Only active approved facts enter a model request; suggested inferences do not.
3. `MemoryTopics` derives topic labels from those facts on demand, formats
   short paragraphs, and retains original IDs, sources and timestamps.
4. The same renderer feeds normal chat and M3.1 planning; memory is ordinary
   lower-trust model context, **not** hidden chain-of-thought, instructions or
   execution permission.
5. No separate persisted summary exists, avoiding stale shadow data after an
   edit, deletion, clear or correction. A richer versioned, revisable profile
   synthesis may be designed separately after evaluation.

## Retrieval

`MemorySelector` now combines lexical token matches and conservative
topic/context matches. A dinner/taco request can retrieve a known food
preference even with different wording; a dining request can retrieve a saved
location; an interview can recall scheduling context. Planning can select up to
six active records within a bounded budget; ordinary chat keeps three.

This is **not** embedding-based or general semantic search. The manual topic
vocabulary will miss paraphrases, disambiguation and subtle contradictions.
No extra provider call occurs on the chat critical path.

## Behavioral constraints

- Use relevant memory to inform tentative defaults; ask fewer questions already
  answered by saved context.
- Treat external information as future lookup, not a mandatory user question.
- Do not overstate ability, execute tools, or present memory as verified fact.
- Do not surface the memory index or pretend it is internal reasoning.
- A user may still disable recall from Memories settings. The visible composer
  defaults to automatic recall, not a per-message memory tool. The API opt-out
  remains. Automatic extraction uses an additional provider request and is
  unchanged by the recall opt-out.

## Model experiment

Added `gemini-3.5-flash` to the default selectable provider catalogue.
Google's documentation lists Gemini 3.5 Flash and Flash-Lite API input/output
as free of charge at the free tier, subject to rate limits. Flash uses medium
thinking by default; Flash-Lite uses minimal by default. No provider thinking
settings, token budgets or guaranteed quotas are changed in this branch.
Configure model availability in AI Studio, and do not assume that switching
models improves retrieval without measuring it.
