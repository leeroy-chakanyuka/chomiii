# M3.2 — provider-neutral tool foundation (in progress)

This is an incremental boundary, **not** a finished authorization gateway,
standalone agent runtime, external connector, or claim of autonomous actions.

## First real tool

`memory.search` is the first working, read-only internal tool. The existing
Gemini adapter already sends native function declarations, retains provider
continuation state, and resumes after a tool result. Chomiii's Java code still
owns the owner/session identity, arguments, limits and result budget.

`ToolDefinition` owns the schema, capability, and READ/WRITE effect without a
provider SDK dependency. `ToolRegistry` discovers `InternalTool` beans.
`ToolTurn` validates arguments, applies the server-side authorization policy,
and executes the tool with a trusted owner and turn context. The default policy
does not expose or execute WRITE tools. Gemini translates the shared definition
into its native function format and resumes the same turn after the result.
See the [architecture document](architecture.md#internal-tool-runtime) for the
execution boundary.

Provider adapters should translate definitions and responses; they must not
import internal memory repositories, choose an owner's credentials, or bypass
the Java gateway. Tests using a fake provider can exercise the same contract.

## To-dos and plan execution

`todo.list` reads the current browser owner's to-dos. `todo.create` and
`todo.complete` require one-time approval for the exact action. The approval
endpoint executes the saved action in the same database transaction that
consumes the approval. Retrying a successful decision returns the stored receipt.
The model cannot make that decision. The approval card appears after the chat
turn commits, and it shows completion only after the write commits.

The existing planner produces a proposal; `PlanRunner` executes the saved
steps in bounded segments through the same registry. It pauses when a write
needs approval. An approved step can continue the plan in a new segment. A
dependent completion can resolve a unique task from an earlier `todo.list`
result; ambiguous or truncated results block the step. Read observations are
stored separately from count-only traces. A revision cancels unfinished work in
the old plan, preserves completed steps as history, and requires fresh approvals.

Execution is limited to local to-dos. There are no persistent grants,
scheduled runs, or automatic model replanning. A user can ask for a revision
in chat or run an unfinished plan again after a transient failure.

### Fictional exam-prep demonstration

Create a disposable loopback PostgreSQL or MySQL database named
`chomiii_eval_*`. Set `CHOMIII_DB_URL`, `CHOMIII_DB_USER`, `CHOMIII_DB_PASSWORD`,
and `EVAL_DISPOSABLE_DB=true`. Run from `backend/`:

```powershell
.\mvnw.cmd '-Dtest=PersonaExamPlanDatabaseTest' '-Deval.mode=integration' test
```

The test seeds the fictional profile, sends the exam-prep request through
chat, and checks that the saved plan waits for approval before creating any
to-dos. It also checks repetition and a second owner's access. No Gemini key
or paid provider call is required.

## M4 — external integrations

M4 uses the M3 gateway to add real provider-neutral external adapters:
first a read-only `web.search` with documented provider, credentials, source
citations and cost controls; then scoped Calendar and Gmail reads/writes and a
guarded MCP client. Direct HTTP/OpenAPI and MCP are transports behind the
same Java policy and tool registry. The OpenAI/Claude/Gemini model provider
must not become the owner of an integration or of its authorizations.

No third-party web API, OAuth flow or MCP client has been added by this
foundation commit. See `docs/external-tool-interoperability-research.md`.
