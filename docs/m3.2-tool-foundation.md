# M3.2 — provider-neutral tool foundation (in progress)

This is an incremental boundary, **not** a finished authorization gateway,
standalone agent runtime, external connector, or claim of autonomous actions.

## First real tool

`memory.search` is the first working, read-only internal tool. The existing
Gemini adapter already sends native function declarations, retains provider
continuation state, and resumes after a tool result. Chomiii's Java code still
owns the owner/session identity, arguments, limits and result budget.

`ToolDefinition` now owns the tool's schema and READ/WRITE effect, with no
dependency on the Gemini SDK or on the `ChatProvider` interface. `InternalTool`
returns that neutral definition. The per-turn `ToolTurn` gateway translates
approved READ definitions into the current provider port's representation;
it **refuses to expose or execute WRITE tools**, because scoped approval and
audited execution do not yet exist. This deliberately prevents an agent from
promoting a model-generated proposal to permission.

Provider adapters should translate definitions and responses; they must not
import internal memory repositories, choose an owner's credentials, or bypass
the Java gateway. Tests using a fake provider can exercise the same contract.

## Remaining M3 stages

- **M3.2 permissions gateway:** trusted per-user execution context, explicit
  per-tool availability, argument schema validation, read privacy controls,
  action-bound approval tokens for writes, audit/trace records and denial tests.
- **M3.3 first approved write:** a small persistent to-do/reminder action using
  real transactional/idempotent execution, not a separate Tasks interface.
  Preserve the useful primitives from PR #5 but resolve Flyway V4 collisions.
- **M3.4 adaptive plan-to-act:** durable structured proposal, tool-observation
  loop, revision of dependent steps, scoped approvals, cancellation and truthful
  completion receipts in the existing chat UI.
- **M3.5 release hardening (proposed, not originally in roadmap):**
  end-to-end scenarios, conflict and privacy evaluations, rate/latency/cost
  budgets, malicious result/prompt injection tests, restart/failure behavior.

## M4 — external integrations

M4 uses the M3 gateway to add real provider-neutral external adapters:
first a read-only `web.search` with documented provider, credentials, source
citations and cost controls; then scoped Calendar and Gmail reads/writes and a
guarded MCP client. Direct HTTP/OpenAPI and MCP are transports behind the
same Java policy and tool registry. The OpenAI/Claude/Gemini model provider
must not become the owner of an integration or of its authorizations.

No third-party web API, OAuth flow or MCP client has been added by this
foundation commit. See `docs/external-tool-interoperability-research.md`.
