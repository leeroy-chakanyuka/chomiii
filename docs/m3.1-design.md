# M3.1 planning design

## Outcome and status

M3.1 turns a person's request into a proposed plan in the existing chat. It is
for people who need to organize everyday commitments without learning tool
names. The intended result is an understandable proposal that uses relevant
memory, identifies missing information, and makes no claim that it acted.

This branch implements a first planning path. It is not an acceptance verdict:
the scenario expectations and semantic results still need independent review.
See the [product vision](product-vision.md), [target architecture](agent-architecture-plan.md),
[memory and planning flow](memory-planning-flow.md), and
[evaluation evidence](m3.1-evaluation.md).

## Routing and chat

`PlanningRouter` uses local patterns to recognize some planning requests.
**Make a plan** explicitly selects planning when the router misses. Normal
chat still uses the existing provider stream; there is no separate model call
to classify a message. The heuristic is not a complete intent classifier.

`ChatStreamService` keeps the existing ownership check, conversation claim,
cancellation, and persistence path. A planning response is buffered until
validation completes. The stream then emits a structured `plan` event and a
readable `delta`. The readable response is stored in the conversation. The
structured event is not stored as a separate durable plan. A malformed plan
emits an error and its raw text is not shown as a successful answer.

## Context and memory

`MemoryService.forPlanning` selects the actual owner-scoped records. It filters
out suggested records before calling the existing lexical `MemorySelector` and
returns at most three records within a 1,400-character selection budget. It
does not infer IDs by searching rendered memory text. If the memory service is
unavailable, planning proceeds without saved memories.

`PlanningService` combines the latest request, bounded complete history,
the current UTC time, and selected memory IDs, source labels, and timestamps.
Memory and time appear in a user-role message, not the system instruction.
The system instruction is the packaged, versioned
`backend/src/main/resources/agent/PLANNING-v1.md` plus catalogue descriptions.
The current message and context share the existing 20-message,
16,000-character limit. The **Use saved memories** opt-out applies to plans.

Active records can be stale or conflict. The prompt asks the model to expose
uncertainty rather than resolve conflicts by timestamp alone. There is no
deterministic semantic conflict detector. No memory is changed by the planner.
The existing post-response learning process can still run after a completed
planning turn and uses a separate provider call.

## Plan contract and validation

`Plan` contains a backend-generated plan ID, goal, summary, memory references,
constraints, questions, and steps. Questions have `planning`, `execution`,
`optional`, or `future_lookup` kinds and identify affected step IDs. Each
step has a model-supplied local ID, title, capability, dependencies, and
Java-derived availability, approval hint, and status. `executed` is always
false. Step IDs are local references, not durable task IDs.

`PlanParser` accepts one JSON object and rejects unknown fields, duplicate
keys, trailing content, missing fields, malformed IDs, and output over 20,000
characters. It allows up to 12 steps, 10 dependencies per step, five memory
references, and five questions. It checks the memory references against the
selected owner-scoped set and checks every capability against the allowed
catalogue. It rejects duplicate, missing, and cyclic dependencies, then orders
the resulting steps with prerequisites first.

`CapabilityCatalog` is descriptive data. It has no executor or connector.
Java derives `not_connected` and `required` for consequential future operations
such as `calendar.update` and `gmail.send`. Those steps are blocked. Approval
hints do not grant authorization. Local `user.prepare` and `user.decide`
steps describe planning work, not an external service call.

The parser rejects a small set of obvious claims that an external action was
completed. This text filter is incomplete and can reject legitimate wording.
Neither it nor a valid dependency graph proves that a proposal is factually or
semantically correct. The model can still omit a necessary step or assign a
misleading description to a known capability.

## Failure and cancellation

Planning uses `ChatProvider` and makes one generation call for the proposal.
`PlanningService` caps model output and cancels its provider stream after 90
seconds. The existing stop endpoint cancels an active planning generation.
Invalid output, timeouts, provider errors, and cancellation do not create a
completed plan. The normal chat stream retains its existing behavior.

## Later milestones

M3.2 can consume the plan contract as a proposal, but must independently bind
authorization to exact actions and arguments. M3.3 can introduce real
connectors only after their availability and permissions are checked in code.
M3.4 can add execution and recovery after action results, idempotency, and
durable state are designed. None of those systems exists in M3.1.
